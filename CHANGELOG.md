# Changelog

## Unreleased

- Settings: one option table (`config::OPTIONS`) now builds `--help`, the commented `launcher.cfg` template, the checks of file values and flags, and the window's labels and descriptions; a test fails when the window and the command line differ. Every window option has a flag and a key: new `--frame-generation`, `--scaler` (remembered in `launcher.cfg`, like `--game` and `--which`, for `screamer-play`), and the Picture tab has a Scaler row on Linux. Messages for bad values come from the table (e.g. `--which needs screamer, screamer2 or screamer-rally, not 4`).
- Settings: the Frame rate choice (30 / 50 / 100 FPS) is now one **Frame generation (100 FPS)** switch (`frame_generation = on|off`, default off): 30 and 50 FPS ran the game the same way, at its fixed 50 Hz. `fps_limit` is still read (60 or more is frame generation on) and is retired when the window saves. Vsync is a plain switch (default on): "As the game" ran DOSBox with vsync on, as On did.
- Window: the Picture tab shows Renderer, Display, Shader and (Linux) Scaler as chip rows, then two pairs of switches (Widescreen and Extended draw distance; Vsync and Frame generation), and a help board that explains the setting under the pointer or the focus; the "Frame Gen ready" summary line is gone. A deadzone, rumble or window size saved in `launcher.cfg` that the chips don't offer gets its own chip and is kept. Disabled choices say why (on hover, to screen readers, and as a line in the Controls and Buttons tabs when the gamepad is off). The box art carries a credit line.
- `--help` prints to stdout and exits 0, and documents the `--settings` exit codes (0, 3, 4), `fullscreen` and `--controllers`. `--check` no longer saves `--game`/`--which` into `launcher.cfg`, and logs what it found.
- The first run writes the recommended look for the screen into `launcher.cfg` (Steam Deck look on a Deck, Enhanced elsewhere). The `launcher.cfg` template now lists every option commented out with its values; a setting left out uses the default.
- An executable with a game's name but an unknown build (SHA-256 not in the edition table) is refused with its SHA-256 and a link to the new issue template, in the window, `--check` and `launcher.log`, instead of being ignored silently.
- `launcher.log` records each launch's decisions: the game and its folder, each executable's edition and SHA-256 and patch count, the fixes left out, the executable, runtime, saves and DOSBox paths, DOSBox's arguments and environment, and how DOSBox ended. `launcher.cfg` is written atomically.
- Windows: the folder picker is the SDK's native dialog (Unicode paths; the PowerShell picker read its output in the console code page).
- Fix (Windows): `ScreamerLauncher.exe` built with MinGW's GNU ld 2.47 crashed before `main` (even `--help`): the linker left 53 of Rust std's `kernel32` imports outside every import descriptor, so they were never resolved. The Windows build now links with LLD (`.cargo/config.toml`; MSYS2's `mingw-w64-x86_64-lld` in CI), and CI runs the Windows build's tests headless under Wine.
- Build on rea-launcher-sdk v0.2.0: the settings window now uses the SDK's widgets (chips, toggles, look and game cards, tabs, folder fields) with Screamer's sizes (`Metrics`), so every control has a keyboard focus ring and reports its name, role, state and disabled reason to screen readers; the current tab is drawn in full white again. Control borders are lighter (`#5d6e90`) to reach 3:1 contrast. The window fits the screen's scale on native Windows and Linux as before. `screamer-play` tests use the SDK's `REA_FUNCTIONS_ONLY`/`REA_PLAY_HERE` convention (the old `SCREAMER_PLAY_DIR`/`SCREAMER_PLAY_FUNCTIONS_ONLY` hooks are gone). On Windows the display and GPU are read through the SDK's display module, and the one remaining Win32 call (WinMM joystick, which also sees non-XInput pads) lives in `src/win32.rs`.
- Build on the shared [rea-launcher-sdk](https://github.com/akitaonrails/rea-launcher-sdk) v0.1.0: the runtime folder sync, save mirroring, folder overlap check, `launcher.cfg` reading and editing, `launcher.log`, window sizing, theme and fonts come from its Rust crates; `screamer-play` runs on its `rea-play.sh` library (shipped beside it in the zip and the AppImage); the AppImage is built by its builder and CI uses its reusable workflows. The settings, files, CLI and `screamer-play` commands are unchanged. Small differences that come with it: unknown `launcher.cfg` keys are noted in `launcher.log`, `;` also starts a comment, saving a commented-out `#key =` setting fills it in place, a `launcher.cfg` that is not UTF-8 is read as Latin-1, `×` is accepted in sizes, `screamer-play` writes the settings window's output to `settings.log` and says when the window was closed or failed, reads `launcher.cfg` next to `ScreamerLauncher` first (as the launcher does) and turns an unknown `scaler` into `fsr`, and on a first save sync a runtime-only save is copied to the saves folder at launch rather than at exit.
- Fix: the runtime folder no longer symlinks files and whole directories into the user's game folder, which let the game write into it. Files are hard-linked (code and drivers only) or copied one at a time into real directories, launcher writes replace whole files, and a manifest of size and modification time brings changed source files in again while keeping the game's saves and replays. Runtime folders from older versions are converted on the next launch.
- Refuse a runtime or saves folder that lies inside the game folder (or contains it), resolving symlinks, `..` and folders that do not exist yet, before anything is written.
- Save sync between the runtime folder and the saves folder no longer overwrites unconditionally. The runtime folder records each save's size and modification time as of the last sync (`.screamer-saves`): at launch a save changed in the saves folder wins (even a restored older backup), otherwise one changed in the runtime folder (a session that ended before its saves were copied back) is copied out; at exit a save is copied back whenever its contents differ. Saves with no recorded state yet: the newer one wins.
- Fix (Linux): `resolution = fullscreen` reached gamescope as `-w fullscreen -h fullscreen`. `screamer-play` now validates `WIDTHxHEIGHT` (any case or spacing), uses the screen size for `fullscreen` (`SCREAMER_SCREEN` overrides the xrandr probe) and keeps 1920x1080 for `original` and anything malformed, including a `0` width or height.
- Fix: a resolution above 1920x1080 (e.g. `3840x2160`) was silently turned into fullscreen when `launcher.cfg` was read. It is now kept as written and shown as its own choice in the Picture tab; only when such a size (above 1920x1080) is larger than the screen (DOSBox cannot open such a window) does the launcher play fullscreen, with a warning. Sizes up to 1080p are passed on unchanged as before, e.g. 1920x1080 on a Steam Deck in Game Mode.
- Fix (Linux): with no `scaler` saved, `screamer-play` defaulted gamescope to `nearest` while `launcher.cfg`'s template and the settings window default to `fsr`; it now uses `fsr` too.
- Fix: the settings window read the monitor size in logical points, so on a scaled display (e.g. a Steam Deck or a 4K screen at 150–200%) it missed the Steam Deck and picked the wrong zoom. The size is now converted to pixels.
- When no settings window can be made (no display or OpenGL), the launcher now plays with the saved settings (and `--settings` exits with code 4, which `screamer-play` already treats as play) instead of stopping with an error. If the window opened and then failed, the game does not start, since it would use settings the player may have just changed. Warnings and errors are written to `launcher.log` next to `launcher.cfg`; on Windows a fatal error is also shown in a message box when the launcher was started the interactive way (settings window, then the game), never for `--check`, `--no-window`, `--settings`, `--controllers` or argument errors from scripts.
- Linux: `screamer-play` now runs each game in its own session and records its pid with its start time, so `status` and `stop` never trust a stale or reused pid and `stop` ends the whole game (gamescope, launcher and DOSBox). Every launch waits for the game to end, and an interrupted `screamer-play` waits for the game it stops (so saves are copied back) before removing the lock. A lock left by an older `screamer-play` (pid only) still counts as running while that process lives, and `stop` ends it. Passing an unknown command with no launcher found is now a clear error instead of `exec ""`. Add `linux/README.md` and the `linux/tests/supervision.sh` test (run in CI).
- Docs: the `rumble` setting is described as what it does (rumble when braking hard in a race), not kerbs, gravel, skids and walls; `--controllers` is described as listing the connected pads (it never logged axis or button events).
- Fix: a symbolic link in the game folder (or a linked `GLIDE2X.OVL` fallback) was hard-linked as the link itself, leaving a broken or user-folder-pointing link in the runtime. The file it points to is now linked or copied.
- Fix (Unix): files copied into the runtime and saves folders were made writable by everyone (mode 0666); only the owner's write permission is added now. A read-only file in the game folder is copied instead of hard-linked.
- Fix: the runtime/saves overlap check refused to launch when a folder could not be canonicalized for a reason other than "not found" (Windows RAM disks, `subst` drives, some network shares); such paths are now compared as written, normalized.
- Fix: runtime staging is more forgiving of unusual game folders. When a CD image is mounted from the game folder, every CD-image file (`.iso`, `.gog`, `.bin`, `.img`, `.cue`, `.ins`, `.ccd`, `.sub`, `.mds`, `.mdf`) and every file its cue sheet names (any case, DOS `\` and `..\` paths) stays there instead of being copied. An unreadable subfolder is skipped with a warning in `launcher.log` instead of stopping the launch, and a symbolic-link loop is not followed.
- CI: check dependencies with `cargo audit` (RustSec advisories) and `cargo deny check` (licences, sources; `deny.toml`).

## 0.6.0 - 2026-11-01

- Add optional E6 extended draw distance to the Enhanced and Steam Deck presets: managed animated objects are visible 20% farther away in Screamer, while Screamer 2 and Screamer Rally use twice the original scenery/object admission radius across all supported renderers.
- Verify every E6 edit against the exact executable SHA-256, original bytes, and LE relocation records; keep the user's game directory read-only and test Original-versus-Enhanced runtime copies byte for byte.
- Add opt-in admission-count telemetry for runtime verification without affecting normal play.
- Retain the in-place Screamer 2/Rally implementation that completed a Rally race segment; discard experimental out-of-line guard variants that reproduced the first-render exit.
- Build Linux zip, AppImage, Windows zip, and recursive corresponding-source archives in GitHub Actions with pinned actions, checksums, and build provenance attestations.
- Link the controller/telemetry hooks directly into the bundled DOSBox on Linux and Windows, and package the required shared runtime libraries.

## 0.5.0

- Initial self-contained launcher for Screamer, Screamer 2, and Screamer Rally with exact-edition fixes, enhanced display presets, modern controller support, and bundled DOSBox Staging.
